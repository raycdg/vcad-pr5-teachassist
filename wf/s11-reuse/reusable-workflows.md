# Повторяющиеся сценарии работы — TeachAssist

> Статус: черновик, версия от 2026-05-04
> Основано на анализе последних 25 коммитов

---

## W1 — Long-horizon реализация по шагам

**Когда применять**: задача требует более 3 независимых шагов, есть риск расхода лимита токенов или необходимость промежуточной проверки

**Входы**:
- Описание задачи в человекочитаемом виде
- Текущее состояние проекта (`git status`, `docs/README.md`)
- Список файлов, которые затронет реализация

**Ожидаемый результат**:
- Документ с разбивкой на шаги (по одному шагу на итерацию)
- После каждого шага — подтверждение пользователя перед продолжением
- Сохранение совместимости с текущим стеком

**Критерии приёмки**:
- План не нарушает ограничения AGENTS.md
- Каждый шаг содержит: описание, файлы для изменения, проверки
- После реализации шага выполнены соответствующие проверки (build/test/lint)

**Форма фиксации**: **template** (`wf/<task-id>/long-horizon-plan-0.md`)

**Почему template, а не тяжелее**:
- Задача уникальна по содержанию, но структура повторяется
- Шаблон легко адаптировать под новую задачу
- Не требует программной логики, только структура документа
- Можно версионировать вместе с кодом

## W2 — Исправление багов с проверкой (fix + verify)

**Когда применять**: обнаружен баг (N+1 запросы, исключения, warnings при сборке), требуется исправление с последующей проверкой

**Входы**:
- Описание проблемы (из логов, тестов или сообщения об ошибке)
- Затронутые файлы (контроллеры, модели, тесты)
- Текущие тесты, покрывающие проблемную область

**Ожидаемый результат**:
- Исправленный код в `backend/` или `frontend/`
- Пройденные проверки (`dotnet build`, `dotnet test`, `npm run lint`)
- Сохранение обратной совместимости API

**Критерии приёмки**:
- `dotnet build` проходит без ошибок
- Существующие тесты не сломаны (`dotnet test`)
- Для backend-исправлений: HTTP-статусы и формат ответов не изменились
- Для frontend-исправлений: `npm run lint` проходит без ошибок

**Форма фиксации**: **checklist** (список проверок перед приёмкой)

**Почему checklist, а не тяжелее**:
- Набор проверок стандартен и небольшой (3-5 пунктов)
- Не требует сложной структуры, только перечень действий
- Легко проверить вручную или автоматизировать в будущем
- Быстро создавать и обновлять

## W3 — Добавление нового endpoint-а (feature + test)

**Когда применять**: требуется добавить новый CRUD-метод или расширить существующий контроллер

**Входы**:
- Спецификация endpoint-а (метод, путь, входные/выходные данные)
- Модель данных (если затрагивает domain models)
- Существующие контроллеры для соблюдения стиля

**Ожидаемый результат**:
- Новый или изменённый файл в `backend/api/Controllers/`
- DTO в `backend/api/DTOs/` (если требуется)
- Минимум один тест в `tests/TeachAssist.Api.Tests/`

**Критерии приёмки**:
- `dotnet build` проходит без ошибок
- `dotnet test` проходит успешно (включая новые тесты)
- Endpoint соответствует стилю существующих (вариант ответа, обработка ошибок)
- Тесты используют InMemory database и xUnit

**Форма фиксации**: **playbook** (пошаговая инструкция с примерами)

**Почему playbook, а не тяжелее**:
- Требует соблюдения нескольких правил (стиль кода, тесты, DTO)
- Нужны примеры из существующего кода
- Порядок действий важен (сначала DTO → контроллер → тесты)
- Skill был бы избыточен, так как логика специфична для каждого endpoint-а

## W4 — Рефакторинг с обновлением документации

**Когда применять**: технический долг, устранение warnings, улучшение читаемости без изменения поведения

**Входы**:
- Список файлов для рефакторинга
- Текущая документация в `docs/README.md`
- Ограничения AGENTS.md (особенно запрет на изменение `backend/migrations/`)

**Ожидаемый результат**:
- Изменённые файлы с улучшенным кодом
- Обновлённая документация в `docs/` (если затронут функционал)
- Пройденные проверки (`dotnet build`, `dotnet test`, `npm run lint`)

**Критерии приёмки**:
- Поведение API не изменилось (все тесты зелёные)
- Документация соответствует изменённому коду
- Отсутствие новых warnings при сборке
- Соблюдены приоритеты: надежность > проверяемость > читаемость

**Форма фиксации**: **command** (набор bash-команд для проверки)

**Почему command, а не тяжелее**:
- Основная работа — это запуск проверок после рефакторинга
- Команды стандартны: `dotnet build`, `dotnet test`, `npm run lint`
- Не требует сложной логики, только последовательность команд
- Легко запомнить и выполнить

## W5 — Завершение практики (step-by-step)

**Когда применять**: выполнение учебных практик (как 5.5, 6.2, 6.3), состоящих из последовательных шагов

**Входы**:
- Описание практики с шагами
- Текущий шаг (step N)
- Инструкции в соответствующих разделах (если есть)

**Ожидаемый результат**:
- Выполненный шаг практики
- Commit с соответствующим префиксом (`add: Выполнена практика Шаг N`)
- Готовность к следующему шагу

**Критерии приёмки**:
- Шаг выполнен согласно описанию
- Пройдены релевантные проверки (build/test/lint)
- Commit message соответствует формату проекта

**Форма фиксации**: **template** (`wf/<practice-id>/step-N.md`)

**Почему template, а не тяжелее**:
- Структура шагов повторяется
- Каждый шаг уникален по содержанию, но форма одинакова
- Легко отслеживать прогресс (какие шаги выполнены)
- Можно использовать один шаблон для всех практик

## W6 — Исправление тестов и настройка тестового проекта

**Когда применять**: перенос тестов в отдельный проект, устранение warnings в тестах, добавление новых тестов

**Входы**:
- Текущая структура тестов (`tests/TeachAssist.Api.Tests/`)
- Список тестов для добавления или исправления
- Используемый фреймворк (xUnit, InMemory database)

**Ожидаемый результат**:
- Тесты собраны в отдельном проекте
- Устранены warnings (xUnit1031, CS8600/CS8602)
- Новые тесты покрывают заявленные сценарии

**Критерии приёмки**:
- `dotnet test` проходит успешно
- Тесты не зависят от реальной БД PostgreSQL
- Все новые тесты содержат минимум одно утверждение (Assert)
- Названия тестов в формате `Method_Scenario_ExpectedResult`

**Форма фиксации**: **checklist** (критерии качества тестов)

**Почему checklist, а не тяжелее**:
- Критерии качества тестов — это перечень правил
- Легко проверить каждый пункт отдельно
- Не требует сложной структуры или примеров кода
- Можно использовать как стандарт для code review

## W7 — UI-полировка существующих компонентов

**Когда применять**: улучшение визуальной части без изменения логики (Vuetify компоненты, стили, валидация форм)

**Входы**:
- Список компонентов для полировки (`frontend/src/views/`, `frontend/src/components/`)
- Текущие маршруты (`frontend/src/router/index.js`)
- Существующие правила валидации форм

**Ожидаемый результат**:
- Изменённые компоненты с улучшенным UI
- Сохранение работоспособности форм и валидации
- Пройденный `npm run lint`

**Критерии приёмки**:
- `npm run lint` проходит без ошибок
- Все существующие маршруты доступны
- Использование только компонентов из официального Vuetify 3 API
- Сохранение всех существующих правил валидации форм

**Форма фиксации**: **playbook** (инструкция с учётом ограничений Vuetify и валидации)

**Почему playbook, а не тяжелее**:
- Требует соблюдения нескольких ограничений (Vuetify API, валидация, маршруты)
- Нужны примеры правильного использования компонентов
- Порядок действий важен (сначала изменения → проверка линтера → проверка маршрутов)
- Skill был бы избыточен, так как изменения специфичны для каждого компонента

## Лучший кандидат для упаковки в skill

### W2 — Исправление багов с проверкой (fix + verify)

**Обоснование**:
1. **Частота использования**: в последних 25 коммитах минимум 6 исправлений багов (fix: add HTML encoding, fix: handle fire-and-forget, fix: resolve N+1, fix: обновлен README, fix: устранить warnings, fix: немного наведен порядок с миграциями)
2. **Стандартный набор проверок**: всегда выполняются `dotnet build`, `dotnet test`, проверка совместимости API
3. **Чёткие стоп-сигналы**: изменение миграций, изменение публичных API без необходимости
4. **Возможность автоматизации**: можно создать skill, который после исправления автоматически запускает проверки и проверяет стоп-сигналы
5. **Не требует сложной логики**: skill может быть простым набором шагов с проверками

**Предварительный состав skill**:
- Вход: описание бага
- Шаг 1: Поиск затронутых файлов (read, grep, glob)
- Шаг 2: Исправление кода в `backend/` или `frontend/`
- Шаг 3: Запуск `dotnet build` и `dotnet test` (или `npm run lint` для frontend)
- Шаг 4: Проверка стоп-сигналов (нет изменений в migrations/, нет изменений контрактов API)
- Шаг 5: Ожидание подтверждения пользователя перед commit

**Преимущества перед playbook**:
- Автоматическое выполнение проверок
- Не нужно вручную запоминать последовательность действий
- Можно добавить дополнительные проверки (например, поиск новых warnings)
