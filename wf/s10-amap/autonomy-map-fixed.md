# Карта границ автономности — TeachAssist (исправленная версия)

> Статус: исправленная версия, от 2026-05-04 (с учётом замечаний ревью)
> Охват: повторяющиеся сценарии работы в репозитории teachassist-5

---

## S1 — Документация

**Допустимый уровень автономности**: средний (самостоятельность в рамках описания реализованного функционала, без принятия архитектурных решений)

**Обязательные артефакты**:
- Файл в `docs/` с расширением `.md`
- Ссылки на реальные файлы кода (формат `path:line`, относительно корня проекта)
- Заголовок с датой и описанием назначения
- Соответствие описания функционала списку реализованных фич в `docs/README.md`

**Проверки перед приёмкой**:
- Отсутствие упоминаний секретов/паролей
- Ссылки на файлы соответствуют реальной структуре проекта
- Соблюдение языка документации (русский)
- Документация не описывает функционал, не реализованный в коде (проверка по наличию соответствующих endpoint-ов/компонентов)

**Стоп-сигналы**:
- Попытка изменить код приложения вместо документации
- Обнаружено описание функционала, не реализованного в текущем коде (противоречие с `docs/README.md` и реальными файлами)
- Попытка принять архитектурное или доменное решение без согласования

**Что не делегируется автоматически**:
- Архитектурные решения и изменение доменной модели
- Удаление или переименование существующих разделов docs/ без согласования
- Добавление в документацию не реализованных планов или фич

## S2 — Read-only исследование

**Допустимый уровень автономности**: высокий (с обязательным соблюдением запрета на чтение `*.prompt` файлов, кроме текущего задания)

**Обязательные артефакты**:
- Краткий отчёт с перечнем найденных файлов
- Ссылки на конкретные строки кода (`file:line`)
- Вывод о соответствии структуры ожиданиям
- Отсутствие в отчёте содержимого файлов `*.prompt`

**Проверки перед приёмкой**:
- Никакие файлы не изменены (проверка `git status` — нет modified/added файлов)
- Использованы только инструменты чтения (read, grep, glob) — подтверждение отсутствия вызовов write/edit/bash в логах сессии
- Отсутствие упоминаний содержимого `*.prompt` файлов в отчёте

**Стоп-сигналы**:
- Попытка выполнить `edit`, `write` или bash-команды, изменяющие файловую систему (например, `rm`, `mv`, перенаправление вывода `>`)
- Предложение изменить код на основе исследования без явного запроса
- Чтение файлов `*.prompt` (кроме текущего задания)
- Рефакторинг по результатам исследования

**Что не делегируется автоматически**:
- Рефакторинг по результатам исследования
- Удаление «неиспользуемого» кода без подтверждения
- Изменение структуры проекта на основе исследования

## S3 — Узкая серверная валидация

**Допустимый уровень автономности**: низкий (требуется явное согласование любых изменений, влияющих на публичный API, включая формат ошибок и правила валидации)

**Обязательные артефакты**:
- Изменённый файл контроллера или DTO в `backend/api/`
- Сохранение обратной совместимости существующих endpoint-ов
- Сообщение о том, какие именно проверки добавлены
- Описание изменений для endpoint-ов без существующих тестов

**Проверки перед приёмкой**:
- `dotnet build` проходит без ошибок
- Существующие тесты не сломаны (`dotnet test`)
- Валидация не меняет HTTP-статусы и формат ответов (включая ошибки) для существующих endpoint-ов
- Для всех изменённых endpoint-ов с существующими тестами подтверждена сохранение контракта
- Для endpoint-ов без существующих тестов добавлено подтверждение ручной проверки контракта

**Стоп-сигналы**:
- Изменение сигнатур публичных методов API
- Изменение формата ответов ошибок (структура JSON, текст сообщений) без согласования
- Добавление новых зависимостей (nuget-пакетов) без запроса
- Изменение `backend/migrations/`
- Любое изменение контракта API (request/response схем) без явной необходимости

**Что не делегируется автоматически**:
- Изменение контрактов API (request/response схем)
- Миграции базы данных
- Изменения в доменной модели (`backend/domain/Models/`)
- Самостоятельное принятие решения о необходимости изменения API

## S4 — Ограничения БД и миграции

**Допустимый уровень автономности**: низкий (только чтение и диагностика)

**Обязательные артефакты**:
- Отчёт о состоянии миграций (`dotnet ef migrations list --context DomainDbContext` и `AuthDbContext`)
- Описание текущей схемы БД на основе `AppDbContext.cs` и `AuthDbContext`
- Перечень существующих таблиц и связей

**Проверки перед приёмкой**:
- Никакие файлы в `backend/migrations/` не изменены
- Команды выполнены только в режиме чтения (без флагов update/add)
- Отчёт не содержит предложений по изменению схемы БД без запроса

**Стоп-сигналы**:
- Любая попытка выполнить `dotnet ef database update`
- Создание новых миграций (`dotnet ef migrations add`)
- Ручное редактирование файлов в `backend/migrations/`
- Попытка изменить конфигурацию подключения к БД

**Что не делегируется автоматически**:
- Применение миграций к базе данных
- Изменение конфигурации подключения к БД
- Удаление или переименование существующих миграций
- Предложение изменений в доменной модели, влияющих на БД

## S5 — UI-полировка

**Допустимый уровень автономности**: средний (в рамках существующих компонентов и стилей, без изменения логики хранилищ и маршрутов)

**Обязательные артефакты**:
- Изменённые файлы во `frontend/src/views/` или `frontend/src/components/`
- Сохранение работоспособности форм и валидации
- Сообщение о том, какие визуальные аспекты изменены
- Сохранение всех существующих атрибутов валидации форм

**Проверки перед приёмкой**:
- `npm run lint` проходит без ошибок (в `frontend/`)
- Все существующие маршруты (согласно `router/index.js`) доступны после изменений
- Использование только компонентов из официального Vuetify 3 API, без несовместимых кастомных обёрток
- Сохранение всех существующих правил валидации форм (required, pattern и т.д.)

**Стоп-сигналы**:
- Изменение структуры роутера (`router/index.js`) без запроса
- Добавление новых зависимостей (`npm install`) без согласования
- Удаление или ослабление существующих правил валидации пользовательского ввода
- Изменение Pinia stores без явной необходимости

**Что не делегируется автоматически**:
- Создание новых страниц (views) или маршрутов
- Изменение Pinia stores без явной необходимости
- Переписывание архитектуры фронтенда
- Изменение логики обработки данных в компонентах

## S6 — Создание тестов

**Допустимый уровень автономности**: высокий (в рамках существующего фреймворка и структуры тестов)

**Обязательные артефакты**:
- Новый или дополненный файл в `tests/TeachAssist.Api.Tests/`
- Использование xUnit и InMemory database (как в существующих тестах)
- Названия тестов в формате `Method_Scenario_ExpectedResult`
- Минимум одно осмысленное утверждение (Assert) в каждом новом тесте

**Проверки перед приёмкой**:
- `dotnet test` проходит успешно
- Тесты не зависят от реальной БД PostgreSQL
- Новые тесты покрывают заявленный сценарий
- Все новые тесты содержат минимум одно утверждение (Assert), проверяющее ожидаемое поведение
- Отсутствие дублирования логики продакшн-кода в тестах

**Стоп-сигналы**:
- Изменение продакшн-кода только для упрощения написания тестов (без исправления существующих багов)
- Добавление реальных секретов или учётных данных в тесты
- Создание тестов, которые меняют состояние вне InMemory
- Изменение интерфейсов контроллеров для тестируемости

**Что не делегируется автоматически**:
- Изменение интерфейсов контроллеров ради тестируемости
- Рефакторинг продакшн-кода в процессе написания тестов (кроме исправления обнаруженных багов)
- Настройка CI/CD для тестов

## S7 — Long-horizon планирование

**Допустимый уровень автономности**: низкий (только исследование, сбор информации и предложения, без реализации)

**Обязательные артефакты**:
- Документ с перечнем шагов и оценкой трудоёмкости
- Ссылки на существующие файлы, которые затронет план (с указанием строк)
- Разделение на итерации (как в docs/README.md)
- Соответствие плана текущему стеку технологий

**Проверки перед приёмкой**:
- План не нарушает ограничения AGENTS.md: не меняет `backend/migrations/`, не меняет публичные API без необходимости, не читает `*.prompt`
- Учтены приоритеты: надежность > проверяемость > читаемость > производительность
- Сохранена совместимость с текущим стеком (VueJS, ASP.NET Core, PostgreSQL)
- План содержит только один шаг реализации на итерацию, с требованием подтверждения после каждого

**Стоп-сигналы**:
- Попытка реализовать более одного шага плана без промежуточного подтверждения результата пользователем
- Изменение кода в процессе планирования
- Предложение сменить стек технологий
- Попытка принять архитектурное решение без согласования

**Что не делегируется автоматически**:
- Архитектурные и доменные решения
- Утверждение приоритетов задач
- Финальное решение о включении фичи в релиз
- Самостоятельная реализация шагов плана

## Правила для всех сценариев

1. **Никогда** не выполнять `git commit` без явного указания пользователя
2. **Никогда** не читать файлы `*.prompt` (кроме текущего задания)
3. Перед изменением логики **обязательно** читать `docs/`
4. При возникновении неуверенности — спросить пользователя
5. Соблюдать приоритеты проекта: надежность > проверяемость > читаемость > производительность
6. Любые изменения публичных API требуют явного согласования, даже если они затрагивают только формат ошибок
7. Все артефакты должны содержать ссылки на конкретные строки кода (формат `path:line`) для верификации
