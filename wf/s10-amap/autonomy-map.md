# Карта границ автономности — TeachAssist

> Статус: черновик, версия от 2026-05-04
> Охват: повторяющиеся сценарии работы в репозитории teachassist-5

---

## S1 — Документация

**Допустимый уровень автономности**: высокий (полная самостоятельность при соблюдении структуры)

**Обязательные артефакты**:
- Файл в `docs/` с расширением `.md`
- Ссылки на реальные файлы кода (формат `path:line`)
- Заголовок с датой и описанием назначения

**Проверки перед приёмкой**:
- Отсутствие упоминаний секретов/паролей
- Ссылки на файлы соответствуют реальной структуре проекта
- Соблюдение языка документации (русский)

**Стоп-сигналы**:
- Попытка изменить код приложения вместо документации
- Противоречие между документацией и существующим кодом

**Что не делегируется автоматически**:
- Архитектурные решения и изменение доменной модели
- Удаление или переименование существующих разделов docs/ без согласования

---

## S2 — Read-only исследование

**Допустимый уровень автономности**: полный (без ограничений)

**Обязательные артефакты**:
- Краткий отчёт с перечнем найденных файлов
- Ссылки на конкретные строки кода (`file:line`)
- Вывод о соответствии структуры ожиданиям

**Проверки перед приёмкой**:
- Никакие файлы не изменены (проверка `git status`)
- Использованы только инструменты чтения (read, grep, glob)

**Стоп-сигналы**:
- Попытка выполнить `edit`, `write` или `bash` с побочными эффектами
- Предложение изменить код на основе исследования без явного запроса

**Что не делегируется автоматически**:
- Рефакторинг по результатам исследования
- Удаление «неиспользуемого» кода без подтверждения

---

## S3 — Узкая серверная валидация

**Допустимый уровень автономности**: средний (требуется подтверждение перед изменением публичного API)

**Обязательные артефакты**:
- Изменённый файл контроллера или DTO в `backend/api/`
- Сохранение обратной совместимости существующих endpoint-ов
- Сообщение о том, какие именно проверки добавлены

**Проверки перед приёмкой**:
- `dotnet build` проходит без ошибок
- Существующие тесты не сломаны (`dotnet test`)
- Валидация не меняет HTTP-статусы успешных запросов

**Стоп-сигналы**:
- Изменение сигнатур публичных методов API
- Добавление новых зависимостей (nuget-пакетов) без запроса
- Изменение `backend/migrations/`

**Что не делегируется автоматически**:
- Изменение контрактов API (request/response схем)
- Миграции базы данных
- Изменения в доменной модели (`backend/domain/Models/`)

---

## S4 — Ограничения БД и миграции

**Допустимый уровень автономности**: низкий (только чтение и диагностика)

**Обязательные артефакты**:
- Отчёт о состоянии миграций (`dotnet ef migrations list`)
- Описание текущей схемы БД на основе `AppDbContext.cs`

**Проверки перед приёмкой**:
- Никакие файлы в `backend/migrations/` не изменены
- Команды выполнены только с флагом `--dry-run` или read-only

**Стоп-сигналы**:
- Любая попытка выполнить `dotnet ef database update`
- Создание новых миграций (`dotnet ef migrations add`)
- Ручное редактирование файлов в `backend/migrations/`

**Что не делегируется автоматически**:
- Применение миграций к базе данных
- Изменение конфигурации подключения к БД
- Удаление или переименование существующих миграций

---

## S5 — UI-полировка

**Допустимый уровень автономности**: средний (в рамках существующих компонентов и стилей)

**Обязательные артефакты**:
- Изменённые файлы во `frontend/src/views/` или `frontend/src/components/`
- Сохранение работоспособности форм и валидации
- Сообщение о том, какие визуальные аспекты изменены

**Проверки перед приёмкой**:
- `npm run lint` проходит без ошибок (в `frontend/`)
- Отсутствие поломок маршрутизации (router/index.js)
- Vuetify-компоненты используются корректно

**Стоп-сигналы**:
- Изменение структуры роутера (`router/index.js`) без запроса
- Добавление новых зависимостей (`npm install`) без согласования
- Нарушение валидации пользовательского ввода

**Что не делегируется автоматически**:
- Создание новых страниц (views) или маршрутов
- Изменение Pinia stores без явной необходимости
- Переписывание архитектуры фронтенда

---

## S6 — Создание тестов

**Допустимый уровень автономности**: высокий (в рамках существующего фреймворка)

**Обязательные артефакты**:
- Новый или дополненный файл в `tests/TeachAssist.Api.Tests/`
- Использование xUnit и InMemory database (как в существующих тестах)
- Названия тестов в формате `Method_Scenario_ExpectedResult`

**Проверки перед приёмкой**:
- `dotnet test` проходит успешно
- Тесты не зависят от реальной БД PostgreSQL
- Новые тесты покрывают заявленный сценарий

**Стоп-сигналы**:
- Изменение тестируемого кода для «удобства тестирования»
- Добавление реальных секретов или учётных данных в тесты
- Создание тестов, которые меняют состояние вне InMemory

**Что не делегируется автоматически**:
- Изменение интерфейсов контроллеров ради тестируемости
- Рефакторинг продакшн-кода в процессе написания тестов
- Настройка CI/CD для тестов

---

## S7 — Long-horizon планирование

**Допустимый уровень автономности**: низкий (только исследование и предложения)

**Обязательные артефакты**:
- Документ с перечнем шагов и оценкой трудоёмкости
- Ссылки на существующие файлы, которые затронет план
- Разделение на итерации (как в docs/README.md)

**Проверки перед приёмкой**:
- План не противоречит ограничениям из AGENTS.md
- Учтены приоритеты: надежность > проверяемость > читаемость
- Сохранена совместимость с текущим стеком (VueJS, ASP.NET Core, PostgreSQL)

**Стоп-сигналы**:
- Попытка реализовать несколько шагов плана без остановки
- Изменение кода в процессе планирования
- Предложение сменить стек технологий

**Что не делегируется автоматически**:
- Архитектурные и доменные решения
- Утверждение приоритетов задач
- Финальное решение о включении фичи в релиз

## Правила для всех сценариев

1. **Никогда** не выполнять `git commit` без явного указания пользователя
2. **Никогда** не читать файлы `*.prompt` (кроме текущего задания)
3. Перед изменением логики **обязательно** читать `docs/`
4. При возникновении неуверенности — спросить пользователя
5. Соблюдать приоритеты проекта: надежность > проверяемость > читаемость > производительность
