# Контракт skill: Bugfix & Verify (Fix + Verify)

> Версия: 0.1-draft | Дата: 2026-05-05 | Источник: W2 из `wf/s11-reuse/reusable-workflows.md`

---

## Название skill
**Bugfix & Verify** (кратко: `bugfix-n-verify`)

## Назначение
Автоматизировать цикл «найти баг → исправить → проверить → подтвердить приёмку» для проекта TeachAssist. Skill гарантирует, что после любого исправления:
- собираются backend и frontend
- проходят все релевантные тесты
- не нарушаются ограничения AGENTS.md (миграции, публичные API)
- изменения задокументированы

## Когда применять
- Обнаружен баг: исключение, N+1 запросы, warning сборки, логическая ошибка, UI-глюк
- Есть воспроизводимое описание проблемы (лог, тест, сообщение пользователя, скриншот)
- Затронутые файлы находятся в `backend/` или `frontend/`
- Требуется быстрое исправление без изменения архитектуры

## Когда НЕ применять
- Нужна новая функциональность или endpoint (→ W3 / playbook)
- Требуется рефакторинг без изменения поведения (→ W4 / command)
- Затрагиваются миграции БД (`backend/migrations/`) — запрещено без явного разрешения
- Требуется изменение публичного контракта API без крайней необходимости
- Задача требует более 3 независимых шагов (→ W1 / long-horizon plan)
- Практический учебный шаг (→ W5 / template)

## Входы (обязательные)
1. **Описание проблемы** — текст ошибки, stack trace, лог, или ссылка на failing test
2. **Список затронутых файлов** (если известен) — пути к `backend/` или `frontend/`
3. **Текущие тесты** — покрывающие проблемную область (если есть)
4. **Контекст** — что сломалось, когда, при каких условиях

## Ожидаемый результат
- Исправленный код в `backend/` и/или `frontend/`
- Прошедшие проверки:
  - `dotnet build` — без ошибок
  - `dotnet test` — все тесты зелёные
  - `npm run lint` — без ошибок (если затронут frontend)
- Обратная совместимость API сохранена (HTTP-статусы и формат ответов не изменились)
- Обновлённая документация в `docs/` (если затронут функционал)
- Готовность к commit (ожидание явного подтверждения пользователя)

## Основные шаги

| # | Шаг | Действие | Проверка / Артефакт |
|---|-----|----------|---------------------|
| 1 | **Локализация** | Поиск затронутых файлов (grep, glob, read) | Список файлов для изменения |
| 2 | **Анализ причины** | Чтение кода, логов, тестов. Определение root cause | Описание причины (1-2 предложения) |
| 3 | **Исправление** | Внесение изменений в код (backend и/или frontend) | Diff изменений |
| 4 | **Build** | `dotnet build` | Успешная сборка без ошибок |
| 5 | **Test** | `dotnet test` | Все тесты прошли |
| 6 | **Lint** | `npm run lint` (если frontend) | Линтер без ошибок |
| 7 | **Стоп-сигналы** | Проверка запрещённых изменений | Нет изменений в migrations/, нет изменения публичных API |
| 8 | **Документация** | Обновление `docs/` при необходимости | Изменения в docs отражают поведение |
| 9 | **Подтверждение** | Ожидание явного разрешения на commit от пользователя | — |

## Стоп-сигналы (немедленная остановка)
- **Изменения в `backend/migrations/`** — запрещено без явного разрешения
- **Изменение публичного контракта API** (HTTP-статусы, формат ответов) — запрещено без явной необходимости
- **Нарушение AGENTS.md** — например, чтение файлов `*.prompt`, пропуск линтера
- **Несовместимость с текущим стеком** — использование библиотек, не заявленных в проекте
- **Более 3 итераций исправлений** без успеха — остановить, предложить W1 (long-horizon)
- **Тесты ломаются после исправления** и причина не ясна — остановить, задокументировать проблему

## Вспомогательные материалы
- `AGENTS.md` — ограничения проекта, приоритеты, структура каталогов
- `docs/README.md` — текущая документация для сверки
- `wf/s11-reuse/reusable-workflows.md` — источник сценария W2
- Справочник команд: `dotnet build`, `dotnet test`, `npm run lint`
- Стек проекта: ASP.NET Core, EF Core, PostgreSQL, xUnit, InMemory DB, VueJS, Vuetify, ESLint

## Критерии приёмки (checklist)
- [ ] `dotnet build` проходит без ошибок
- [ ] `dotnet test` проходит успешно (все тесты зелёные)
- [ ] `npm run lint` проходит без ошибок (если затронут frontend)
- [ ] HTTP-статусы и формат ответов API не изменились
- [ ] Нет изменений в `backend/migrations/`
- [ ] Нет изменений публичных API без явной необходимости
- [ ] Документация в `docs/` обновлена (если затронут функционал)
- [ ] Commit message соответствует формату проекта (`fix: ...`)
- [ ] Получено явное подтверждение пользователя на commit

2. Как обрабатывать ситуации, когда баг связан с данными в PostgreSQL, а не с кодом?
3. Нужен ли отдельный шаг для создания regression-теста при каждом исправлении?
4. Как формализовать «публичный контракт API» — достаточно ли проверки статус-кодов, или нужен контрактный тест (Swagger diff)?
5. Стоит ли включать проверку покрытия тестами (`skill: test-coverage`) в обязательные шаги?
