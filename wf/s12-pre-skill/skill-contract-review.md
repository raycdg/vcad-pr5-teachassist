## Замечания ревьювера

### 1. Слишком широкий триггер применения

- **«Обнаружен баг: исключение, N+1 запросы, warning сборки, логическая ошибка, UI-глюк»** — слишком широко. «Логическая ошибка» может требовать изменения бизнес-логики и затрагивать несколько модулей — это уже не «быстрое исправление». «UI-глюк» overlaps с W7 (UI-полировка), граница размыта.
- **«Требуется быстрое исправление без изменения архитектуры»** — слово «быстрое» субъективно и не операционализовано. Что считать быстрым — 1 итерацию? 30 минут?

**Уточнить**: сузить «Когда применять» до конкретных симптомов с примерами, добавить количественный лимит (например, «затрагивает не более 3 файлов»). Уточнить границу с W7.

---

### 2. Дублирование project rules

- Стоп-сигналы «Изменения в `backend/migrations/`» и «Нарушение AGENTS.md — чтение файлов `*.prompt`» — это уже прямые цитаты из AGENTS.md. Skill не должен дублировать глобальные запреты, он должен на них **ссылаться**.
- «Соблюдены приоритеты: надежность > проверяемость > читаемость» не упомянут, но подразумевается в критериях. Это тоже из AGENTS.md.

**Уточнить**: заменить дублирование на ссылку (например, «Применяются все ограничения AGENTS.md, включая: запрет на изменение migrations/...»).

---

### 3. Скрытая автоматизация спорных решений

- **Шаг 2 «Анализ причины»** — кто определяет, что причина найдена верно? Skill сам решает, когда остановиться и перейти к исправлению. Это может привести к ложной диагностики.
- **Шаг 7 «Стоп-сигналы»** — идёт *после* исправления. По логике, стоп-сигналы должны проверяться *до* и *во время* изменений, а не постфактум. Если исправление уже затронуло миграции — поздно останавливать.
- **«Обновлённая документация в `docs/` (если затронут функционал)»** — кто решает, затронут ли функционал? Это субъективное решение без чёткого критерия.

**Уточнить**: перенести стоп-сигналы на шаг 0 (pre-flight check), добавить явный критерий «документация обновляется, только если изменился формат ответа endpoint-а или добавлено/удалено поле».

---

### 4. Слабые критерии приёмки

- **«HTTP-статусы и формат ответов API не изменились»** — как проверяется? Нет инструмента или метода. Сейчас это «верить на слово».
- **«Все тесты зелёные»** — не различает существующие и новые тесты. Если баг не покрыт тестами, `dotnet test` пройдёт, но исправление не проверено.
- **«Документация обновлена (если затронут функционал)»** — тавтология, условие «если» делает критерий непроверяемым.
- **«Commit message соответствует формату»** — skill не должен требовать commit, он должен готовить к нему. Критерий лишний, это ответственность W5.

**Уточнить**: добавить способ проверки API (например, `diff git` по файлам контроллеров/DTO); разделить критерии на обязательные и условные; убрать пункт про commit.

---

### 5. Стоп-сигналы, которые стоит сделать явнее

| Текущий | Проблема | Предложение |
|---------|----------|-------------|
| «Изменение публичного контракта API — запрещено без явной необходимости» | «Явная необходимость» — субъективно | Заменить на «Любое изменение DTO, сигнатуры контроллера или HTTP-статуса требует явного разрешения пользователя **до** исправления» |
| «Тесты ломаются после исправления и причина не ясна» | Что делать, если причина ясна, но исправить невозможно в рамках этого skill? | Добавить «или исправление требует изменения структуры тестов → перейти к W6» |
| Нет стоп-сигнала для **frontend без линтера** | Если в проекте нет настроенного `npm run lint` или он не запускается, skill продолжит работу без проверки | Добавить «Frontend-исправления без рабочего `npm run lint` требуют подтверждения пользователя» |
| Нет стоп-сигнала для **отсутствия тестов** | Если проблемная область не покрыта тестами, skill не имеет способа верифицировать исправление | Добавить «Если проблемная область не покрыта тестами — предупредить пользователя и предложить добавить тест (→ W6)» |

|----------------|--------------|

| Стоп-сигналы | Сделать бинарными (да/нет), убрать субъективные формулировки |
| Открытые сомнения | Решить вопросы 1, 3, 4 до стабилизации контракта — они влияют на шаги и критерии |
