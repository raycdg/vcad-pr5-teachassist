# Долгосрочный план: Авторизация с ролями и личный кабинет

## Цель задачи
Добавить в проект TeachAssist систему аутентификации и авторизации пользователей с поддержкой трёх ролей (преподаватель, менеджер, администратор), разделением функций по ролям и личным кабинетом пользователя с возможностью смены пароля и email.

## Роли
- **Преподаватель**: создаёт предметы, редактирует задания предметов, добавляет курсы, редактирует оценки в своих курсах; не может изменять предметы, задания, курсы и оценки, которые не создавал
- **Менеджер**: полный доступ ко всем функциям по группам, студентам, предметам, заданиям, курсам и оценкам; добавляет преподавателей к курсам и предметам
- **Администратор**: все функции менеджера плюс управление пользователями системы

---

## Этап 1: Инфраструктура аутентификации (JWT)

**Задача этапа**: Добавить в backend базовую инфраструктуру JWT-аутентификации — пакеты, конфигурацию, модель пользователя, вход. Регистрация не требуется — пользователей создаёт только администратор.

**Что сделать**:
- Установить пакет `Microsoft.AspNetCore.Authentication.JwtBearer` и `Microsoft.AspNetCore.Identity.EntityFrameworkCore`
- Создать модель `AppUser` (наследник `IdentityUser`) с полями: Id, Email, PasswordHash, IsDeleted, CreatedAt, UpdatedAt
- Настроить глобальный фильтр EF Core на `IsDeleted` в DbContext
- Настроить Identity + JWT в `Program.cs` (AddAuthentication, AddAuthorization, AddIdentity)
- Создать `AuthController` с endpoint: POST `/api/auth/login`
- Создать миграцию БД для таблиц Identity
- Добавить seed-данные: создание учётной записи администратора по умолчанию при старте (`admin@teachassis.local` / пароль `admin`)
- На frontend: добавить страницу `/login`, сохранить JWT в localStorage, добавить axios-интерцептор для подстановки `Authorization: Bearer <token>`
- Добавить роут-гард для защиты всех страниц кроме `/login`

**Ожидаемый артефакт**: Работающий flow входа, JWT выдаётся и принимается backend, frontend перенаправляет неавторизованных на `/login`. В БД есть учётная запись админа по умолчанию.

**Критерий завершения**:
- Можно войти в систему под `admin@teachassis.local` / `admin`
- JWT валидируется на backend
- Страницы frontend недоступны без токена (редирект на `/login`)
- Все существующие тесты backend проходят (или обновлены с mock auth)

**Сигналы остановки**:
- Конфликты с существующей конфигурацией EF Core (например, проблемы с несколькими DbContext)
- Непредвиденные проблемы с CORS при отправке токена с frontend
- Требуется решение по refresh-токенам (выходит за рамки этапа)

## Этап 2: Управление пользователями (администратор)

**Задача этапа**: Реализовать функционал администратора по созданию и управлению пользователями системы.

**Что сделать**:
- Backend: создать `UsersController` с endpoints (доступ только Admin):
  - GET `/api/users` — список всех пользователей (с флагом `?includeDeleted`) с фильтрацией по роли
  - GET `/api/users/{id}` — данные пользователя
  - POST `/api/users` — создать пользователя с заданным email, паролем и ролью
  - PUT `/api/users/{id}/role` — изменить роль
  - PUT `/api/users/{id}/reset-password` — сбросить пароль
  - DELETE `/api/users/{id}` — мягкое удаление (`IsDeleted = true`), пользователь исключается из фильтров по умолчанию
  - POST `/api/users/{id}/restore` — восстановить удалённого пользователя
- Frontend: создать страницу `/admin/users` (доступ только Admin) с таблицей пользователей, формами создания/редактирования, индикацией удалённых
- Добавить защиту роутов frontend: `/admin/*` доступны только Admin
- Добавить базовую роль `Admin` через Identity RoleManager, создать политику `RequireAdmin`

**Ожидаемый артефакт**: Администратор (учётка по умолчанию) может просматривать, создавать, редактировать роли, мягко удалять и восстанавливать пользователей через UI.

**Критерий завершения**:
- Администратор входит под `admin@teachassis.local` / `admin`
- Администратор видит список всех пользователей с фильтрацией
- Администратор может создать пользователя с заданной ролью (Teacher, Manager, Admin)
- Администратор может изменить роль пользователя
- Администратор может сбросить пароль пользователя
- Удалённые пользователи исключаются из обычного списка, но видны с флагом `?includeDeleted`
- Удалённые пользователи не могут войти в систему
- Менеджер и преподаватель НЕ имеют доступа к `/api/users` и `/admin/users` (403)
- Написаны тесты на контроллер пользователей

**Сигналы остановки**:
- Требуется функция импорта пользователей из файла (CSV/Excel)
- Обнаружена необходимость в логировании действий администратора
- Soft delete ломает уникальность email (удалённый пользователь занимает email)

## Этап 3: Система ролей и политики авторизации

**Задача этапа**: Реализовать ролевую модель (преподаватель, менеджер, администратор) и политики авторизации на backend.

**Что сделать**:
- Создать роли `Teacher`, `Manager`, `Admin` через Identity RoleManager (если не созданы)
- Создать политики авторизации в `Program.cs`: `RequireTeacher`, `RequireManager`, `RequireAdmin`
- Добавить claims к JWT: `role`, `userId`, `email`
- Создать frontend-стор `auth.js` (Pinia) для хранения информации о текущем пользователе (role, email, userId)
- Добавить отображение роли и имени пользователя в `App.vue`
- Закрыть все существующие API endpoints политиками авторизации (Teacher+ для чтения, Manager+ для CRUD групп/студентов)

**Ожидаемый артефакт**: Пользователи имеют роли, JWT содержит роль, политики `[Authorize(Policy = "...")]` работают на backend, frontend знает роль текущего пользователя.

**Критерий завершения**:
- Роли существуют и назначаются пользователям
- JWT содержит claim `role`
- Политики `[Authorize]` с ролями корректно разрешают/запрещают доступ
- Frontend отображает роль и имя пользователя в шапке

**Сигналы остановки**:
- Требуется более гранулярная система разрешений (permissions) вместо ролей
- Возникает необходимость в иерархии ролей (наследование разрешений)
- Обнаружено, что текущая структура контроллеров не подходит для ролевой авторизации

## Этап 4: Личный кабинет пользователя

**Задача этапа**: Создать личный кабинет с возможностью смены пароля и email.

**Что сделать**:
- Backend: создать `AccountController` с endpoints:
  - GET `/api/account/profile` — получить данные текущего пользователя
  - PUT `/api/account/email` — сменить email (с подтверждением через старый пароль)
  - PUT `/api/account/password` — сменить пароль (требует старый пароль)
- Frontend: создать страницу `/profile` с формами смены email и пароля
- Frontend: добавить ссылку на профиль в меню пользователя в `App.vue`
- Валидация: email должен быть уникальным, пароль должен соответствовать требованиям Identity

**Ожидаемый артефакт**: Авторизованный пользователь может просмотреть свой профиль, сменить email и пароль через UI.

**Критерий завершения**:
- GET `/api/account/profile` возвращает данные текущего пользователя
- Смена email работает и валидирует уникальность
- Смена пароля работает и требует старый пароль
- Формы на frontend имеют валидацию и показывают ошибки
- После смены email/token пользователь остаётся в системе

**Сигналы остановки**:
- Требуется подтверждение email через ссылку (выходит за рамки, нужен SMTP flow)
- Обнаружены проблемы с инвалидацией JWT при смене пароля (нужен механизм blacklist/rotation)
- Требуется двухфакторная аутентификация

## Этап 5: Авторизация на уровне ресурсов (преподаватель — свои ресурсы)

**Задача этапа**: Реализовать ограничение доступа преподавателя только к собственным ресурсам (предметы, задания, курсы, оценки) с поддержкой нескольких преподавателей на одну дисциплину/курс. Преподаватель может видеть все дисциплины и создавать курсы на любую дисциплину.

**Что сделать**:
- Добавить связь многие-ко-многим `AppUser` ↔ `Discipline` через таблицу `DisciplineTeachers` (`DisciplineId`, `TeacherId`)
- Добавить связь многие-ко-многим `AppUser` ↔ `Course` через таблицу `CourseTeachers` (`CourseId`, `TeacherId`)
- Создать authorization handler `ResourceOwnerAuthorizationHandler` для проверки принадлежности ресурса пользователю
- Обновить контроллеры:
  - `DisciplinesController`: GET (без фильтра) — преподаватель видит все дисциплины; POST — преподаватель может создавать дисциплины; PUT/DELETE — преподаватель редактирует/удаляет только дисциплины, где он назначен
  - `TasksController`: преподаватель редактирует только задачи дисциплин, где он назначен
  - `CoursesController`: GET — преподаватель видит свои курсы; POST — преподаватель может создать курс на любую дисциплину (не только свою); PUT/DELETE/PATCH — преподаватель редактирует только курсы, где он назначен
  - `CoursesController` (grades): преподаватель редактирует только оценки в курсах, где он назначен
- Менеджер и администратор имеют полный доступ ко всем ресурсам
- Добавить endpoint для менеджера: POST `/api/disciplines/{id}/assign-teacher`, POST `/api/courses/{id}/assign-teacher`, DELETE `/api/disciplines/{id}/teachers/{teacherId}`, DELETE `/api/courses/{id}/teachers/{teacherId}`

**Ожидаемый артефакт**: Преподаватель не может изменить ресурсы, к которым не назначен. На одну дисциплину/курс можно назначить нескольких преподавателей. Преподаватель видит все дисциплины и может создать курс на любую дисциплину. Менеджер управляет назначениями.

**Критерий завершения**:
- На одну дисциплину/курс можно назначить нескольких преподавателей
- Преподаватель GET `/api/disciplines` возвращает все дисциплины
- Преподаватель НЕ может PUT/DELETE дисциплину, где он не назначен (403)
- Преподаватель может POST `/api/courses` с `DisciplineId` любой дисциплины
- Преподаватель при создании курса видит список всех дисциплин
- Преподаватель GET `/api/courses` возвращает только курсы, где он назначен
- Менеджер может назначить/снять преподавателя с дисциплины/курса через API
- Менеджер и администратор имеют полный доступ ко всем ресурсам
- Написаны тесты на authorization handlers

**Сигналы остановки**:
- Обнаружена необходимость в аудите (кто и когда изменил ресурс)
- Логика владения ресурсами сложнее, чем ожидалось (например, наследование владения задачами от дисциплины)
- Требуется разделение ролей преподавателей внутри дисциплины (ведущий/сопреподаватель)

## Этап 6: Frontend — ролевое отображение и защита UI

**Задача этапа**: Полностью адаптировать frontend под ролевую модель — скрыть/показать элементы UI в зависимости от роли, защитить роуты.

**Что сделать**:
- Создать директиву/компонент `v-role="teacher"` для условного отображения элементов
- Обновить навигацию в `App.vue`: показывать ссылки в зависимости от роли
- Обновить все существующие страницы:
  - `Disciplines.vue`: преподаватель видит только свои, кнопка создания только у Teacher+
  - `Tasks.vue`: преподаватель редактирует только задачи своих дисциплин
  - `Courses.vue`: преподаватель видит только свои курсы
  - `CourseProgress.vue`: преподаватель редактирует оценки только в своих курсах
  - `Groups.vue`, `GroupDetail.vue`: доступны только Manager+ (преподаватель не управляет группами)
  - `Students.vue`: доступны только Manager+ (преподаватель не управляет студентами напрямую)
- Добавить роут-гарды с проверкой ролей в `router/index.js`
- Добавить страницу «Доступ запрещён» (403)

**Ожидаемый артефакт**: UI полностью соответствует ролевой модели — пользователь видит только то, что ему разрешено.

**Критерий завершения**:
- Преподаватель видит только свои дисциплины, задачи, курсы и оценки
- Преподаватель НЕ видит ссылки на управление группами и студентами
- Менеджер видит все ресурсы и все ссылки навигации кроме админских
- Администратор видит всё плюс ссылку на управление пользователями
- Прямой переход на запрещённый роут показывает 403
- ESLint проходит без ошибок

**Сигналы остановки**:
- Требуется более сложная логика отображения (например, частичная видимость данных)
- Обнаружены UX-проблемы: пользователю непонятно, почему он не видит данные
- Требуется адаптация мобильных видов под ролевую модель

## Зависимости между этапами

```
Этап 1 (JWT инфраструктура, seed админа)
  ↓
Этап 2 (Управление пользователями — Admin)
  ↓
Этап 3 (Роли и политики)
  ↓
Этап 4 (Личный кабинет)
Этап 5 (Авторизация ресурсов, многие-ко-многим)
  ↓
Этап 6 (Frontend ролевое отображение)
```

## Примечания
- Все изменения backend должны сопровождаться обновлением миграций БД
- Все изменения frontend должны проходить `npm run lint` без ошибок
- Существующие ~100 тестов backend должны продолжать проходить после каждого этапа
- Изменения в API должны быть документированы в `docs/`
